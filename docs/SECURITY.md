# Безпека та Content Security Policy (CSP)

Проєкт використовує суворі налаштування безпеки для захисту даних користувачів та запобігання атакам типу XSS (Cross-Site Scripting) та Clickjacking.

## Content Security Policy (CSP)

CSP - це механізм безпеки, який дозволяє обмежити ресурси (скрипти, стилі, зображення), які браузер може завантажувати для вашого сайту.

### Налаштування для Firebase та Google Services

Оскільки проєкт використовує Firebase для авторизації та Google Cloud Storage для зберігання зображень, у політиці CSP дозволені наступні домени:

| Директива | Дозволені ресурси | Призначення |
|-----------|-------------------|-------------|
| `connect-src` | `identitytoolkit.googleapis.com`, `securetoken.googleapis.com`, `*.googleapis.com` | Авторизація Firebase та API Google |
| `img-src` | `storage.googleapis.com`, `*.firebasestorage.app`, `*.googleusercontent.com` | Зображення вин, виноробень та аватари |
| `script-src` | `apis.google.com`, `www.gstatic.com` | Скрипти Google SDK |
| `font-src` | `fonts.gstatic.com` | Шрифти Google Fonts |
| `frame-src` | `*.firebaseapp.com`, `www.youtube.com`, `youtube.com` | Віджети Firebase та відео YouTube |

### Де налаштовується CSP?

Політика CSP налаштована у двох місцях:

1.  **Бекенд (`backend/src/index.ts`)**: Використовується бібліотека `helmet`. Це захищає API-запити та загальну поведінку сервера.
2.  **Фронтенд (`frontend/vercel.json`)**: Заголовок `Content-Security-Policy` прописаний у конфігурації Vercel. Це критично важливо, оскільки Vercel віддає HTML-файл, і саме ці налаштування браузер застосовує першими.

**Важливо:** При додаванні нових сторонніх сервісів (наприклад, нові карти або аналітика) необхідно оновити обидва файли, інакше браузер заблокує запити.

## CORS (Cross-Origin Resource Sharing)

Доступ до API обмежений через CORS. Дозволені домени налаштовуються через змінну оточення `CORS_ORIGIN` на бекенді. Також підтримуються піддомени на Vercel (`*.vercel.app`) для зручності попереднього перегляду розгортань.

## Rate Limiting

Для захисту від Brute-force атак та перевантаження сервера встановлено обмеження:
- **Ліміт:** 1000 запитів за 15 хвилин на один IP.
- Ендпоінти `/api` захищені автоматично.

## Валідація та Санітизація

1.  **Zod (Frontend):** Усі форми валідуються на стороні клієнта за допомогою схем Zod перед відправкою.
2.  **Joi (Backend):** Всі вхідні дані на бекенді проходять повторну сувору валідацію.
3.  **XSS Protection (Frontend):** Утиліта `stripHtml` використовує безпечні регулярні вирази для видалення тегів, уникаючи прямої маніпуляції `innerHTML`, що запобігає виконанню шкідливих скриптів при відображенні прев'ю.
4.  **sanitize-html (Backend):** Дані, які можуть містити HTML, очищуються перед збереженням у базу даних.

## Обробка автентифікації

Для забезпечення швидкості та безпеки запитів:
- **Кешування токенів:** ID-токени Firebase кешуються у пам'яті фронтенду.
- **Синхронні запити:** Axios-інтерцептор додає токен до заголовків синхронно, що усуває затримки та запобігає станам гонки (race conditions).
- **Слухачі:** Оновлення кешу токена відбувається автоматично через `onIdTokenChanged`.

## Firebase Admin & RBAC
...
Доступ до адміністративних функцій регулюється через **Custom Claims** у Firebase:
- Ролі: `USER`, `WINERY_OWNER`, `ADMIN`.
- Перевірка ролей здійснюється за допомогою `roleMiddleware` на бекенді.
